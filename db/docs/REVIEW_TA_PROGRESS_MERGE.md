## Findings

### BLOCKER

### SHOULD-FIX
1. **Stale "11 screens / ScreenStub / Pass 1" doc comment in `App.tsx`** — `client/src/App.tsx:14-16` still reads "The 11 in-app screens render as `<ScreenStub/>` placeholders during Pass 1; the next pass replaces each with the real body." `NAV_ITEMS` now has 13 entries (`client/src/lib/nav.ts:40-160`), none of which render `ScreenStub` — they're all real pages, including the two this batch adds (`Writing`, `Progress`). This predates the current merge (not introduced by it) but the review task explicitly asked to check for it, and it is now actively misleading to the next engineer who opens the file. `nav.ts`'s own header comment was correctly generalized in this same merge window ("the app's screens" instead of "the 11 screens", `client/src/lib/nav.ts:2`) — `App.tsx`'s header just never got the same treatment.
2. **`Progress.tsx` can show `MockBadge` and the fatal-error card simultaneously** — `client/src/pages/Progress.tsx:195` renders `MockBadge` whenever `hist.isMock` is true, independent of the `fatalError` branch below it (`:208-210`). Per `useEndpointOrMock`'s contract (`client/src/hooks/useEndpointOrMock.ts:220-231`), a real-fetch failure sets `isMock: true` (empty mock data) *and* carries the real error forward. Since the mock fallback here is deliberately empty (`loadProgressHistoryMock`, `Progress.tsx:117-120`), `snapshots.length === 0` so `fatalError` is non-null too — the user would see the dev-only mock badge stacked above an error card in the same render. Low severity (the badge is `PROD`-gated per the hook's own docstring, so end users never see it; only visible to developers in dev builds), but it's a slightly confusing combination worth a one-line guard (`hist.isMock && fatalError === null`) for internal consistency with the "never dress a failed fetch up as a mock success" intent stated in the file's own threat-model comment (`:33-35`).

### NIT
1. `Progress.tsx:426-428,436` computes `startX`/`endX` as raw pixel values in the `640×260` viewBox but converts them to `%` against `W` for the hit-column `left`/`width` — correct, but relies on the SVG and the absolutely-positioned button sharing the exact same aspect-ratio container; a future CSS change to `.km-progress__chartwrap` that breaks `aspect-ratio` parity (not present today — not verified as an actual bug, just a coupling worth a comment) would silently misalign hit targets from the visual line. Not asserted by any test since jsdom doesn't lay out real pixels.
2. `diagnostic.ts:1305-1309` docstring for `/history` is excellent (names the exact attack, the defense, and the tie-break rationale) — worth using as the template for future route docstrings in this codebase; called out under PRAISE below too.

### PRAISE
1. **`GET /diagnostic/history` security posture is exemplary** (`server/src/routes/diagnostic.ts:1311-1341`): parameterized `WHERE user_id = $1`, `deleted_at IS NULL` soft-delete filter, deterministic `ORDER BY captured_at ASC, id ASC` tie-break, 200-with-empty-array (never 404) matching the established `/latest` posture, and a docstring that names the exact OWASP category (BOLA/IDOR) and the specific defense — exactly the Bar §0 P0 standard ("name the attack, name the defense").
2. **Cross-user isolation test is done right, not just present** (`server/tests/routes/diagnostic.test.ts:862-877`): it doesn't just assert user B sees `[]` (which would pass even if the query had no `WHERE user_id` clause and simply had no rows for a fresh DB) — it also asserts user A still sees their own single snapshot afterward, proving the isolation is real scoping and not a blanket-empty response. This is the "would this test have failed on a genuinely broken pre-fix" bar done correctly.
3. **`Progress.tsx` empty/single-attempt geometry is provably safe**, not just apparently safe: `xFor` (`:135-139`) explicitly special-cases `n <= 1` before the `/(n-1)` division, `overallOf` (`:89-93`) returns `null` on zero dimensions instead of `NaN`, and `consecutiveRuns` (`:155-168`) only draws a `<polyline>` when a run has `≥2` points — a single point renders as a dot only, never a degenerate/zero-length line. All three edge cases are also asserted in `Progress.test.tsx` (empty → invite card, 1 attempt → markers + note, `n=1` chart aria-label), not just implemented defensively and left untested.
4. **Answer-tampering defense is carried through consistently across the whole stack** — `ServerItem.correctAnswer`/`explain` are never serialized (`toClientItem`, `diagnostic.ts:137-151`), `DiagnosticLiveItem` in `domain.ts` has a comment explicitly forbidding an `answer` field from ever being re-added (`domain.ts:400-407`), and `Progress.tsx`'s own threat-model comment confirms the page is read-only with no client-supplied identifiers. This is a genuinely coherent security invariant maintained across 5 independently-authored worktrees.
5. **Test adequacy is real**: the `/history` server tests (`diagnostic.test.ts:813-877`) would fail on the pre-fix (no-route) code with a 404, would fail if the `WHERE user_id` predicate were dropped or wrong (the isolation test), and would fail if ordering were reversed or non-deterministic (the two-snapshot ordering test asserts `first`/`second` by score, not just length). The client `getHistory` tests (`diagnostic.test.ts` client, lines 277-322) cover empty passthrough, URL/signal threading, and error rethrow.
