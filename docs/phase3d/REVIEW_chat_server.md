# Phase 3D — Chat Server Review (F-037 prompt, F-036 naming, F-035 file attach)

**Reviewer:** independent senior reviewer (30yr), report-only, did not write this code.
**Branch:** `feat/phase3d-chat` vs `rebuild`.
**Scope:** `server/src/services/claude/prompts/conversation.ts` (F-037 diff), `server/src/routes/conversation.ts` (`POST /:id/name`, `POST /:id/file`), `server/tests/routes/conversation.test.ts`, `server/tests/services/conversation-prompt.test.ts`, plus the client call sites in `client/src/pages/Chat.tsx` and `client/src/services/conversation.ts` and the server-side enforcement in `server/src/services/docAttach.ts`.

## Verdict

**PASS.** 0 BLOCKERS. The F-037 prompt change is a small, well-targeted diff that genuinely instructs shorter, chat-like replies while preserving corrections, register-matching, and the anti-injection structure. The `/name` route is idempotent in the sense that matters (no second Claude call once a title is persisted, verified by tests with a call counter) and is fully user-scoped; the one gap — a narrow concurrent-request race — is bounded by `expensiveLimiter` and does not constitute "runaway" spend. The `/file` route validates everything server-side (size, declared-mime allowlist, and critically the actual UTF-8 byte content) and never trusts the client; it is user-scoped and transactional.

## Findings

### PRAISE

- **P-1 — the brevity instruction is well-constructed and should work.** `DEFAULT BREVITY (F-037)` gives a concrete shape ("1–3 short sentences: react/answer, at most one correction, one follow-up question") rather than a vague "be concise," and explicitly forbids the failure mode it's fixing ("Never pad a complete short answer with restatement or filler"). `EXPAND ONLY ON REQUEST` gives the model a clear, example-anchored trigger ("설명해 주세요", "더 자세히", "왜 그래요?", "more detail", "a request for a full dialogue/essay/summary") for the escape hatch, and bounds it ("stop once you've covered what was actually asked"). Rule 2 in the numbered list reinforces the same instruction a second time in the format-rules section, which is good redundancy for an LLM system prompt (the model sees the constraint twice, once as prose guidance and once as a hard rule). Rule 5 (new) extends the same discipline to `englishNote` ("never a running translation or a second essay"), closing the obvious loophole where the model complies on `korean` but pads the English side instead. This is exactly the right shape of prompt edit for the stated product problem ("very long and blocky").
- **P-2 — casual mode instruction is consistent, not contradictory.** The old casual instruction ("Keep turns to 2–4 sentences") was loosened to defer to the shared brevity rule ("Follow the default brevity rule (short turn, one follow-up question)") rather than hard-coding a second, slightly different sentence count that could drift from the header. The correction guidance was tightened in the same edit ("keep the correction to a few words, not a lecture") — this is additive discipline in the same direction as the header change, not a competing instruction. No mode instruction (business/research/topik_prep/register_drill) conflicts with the brevity rule: `topik_prep`'s "add a brief note flagging TOPIK patterns" and `register_drill`'s "explicitly mark which register" both target `englishNote`, not `korean` — consistent with Rule 3 ("include the switch INSIDE englishNote, not in korean").
- **P-3 — `/file` server-side validation is genuinely defense-in-depth, not trust-the-client.** The docAttach.ts header explicitly documents the threat model (MIME spoofing, memory/DoS, prompt injection, path traversal, JSONB bloat) and every one of those has a corresponding server-side check independent of what the client sends, backed by tests that use real attack shapes (actual PNG magic bytes declared as `text/plain`, actual injection-marker text, actual `../../etc/passwd.txt` traversal attempt) rather than mocked validators.
- **P-4 — test suite exercises real Korean corpus text and real edge cases**, not placeholder strings: NFC-expansion-past-cap, UTF-16 surrogate-boundary truncation (would 500 at the jsonb INSERT if mishandled), and the full idempotency/IDOR/concurrency-adjacent matrix for both new routes. This is exactly the standard the project holds itself to (see the "test with real corpus data" standing feedback) and the tests meet it.

### SHOULD-FIX

- **S-1 — `/name` is not exactly-once under concurrent first calls (routes/conversation.ts:1009-1099).** The route reads `title`, and only calls Claude (`proxy.nameConversation`) if `title === null`, then later does `UPDATE ... WHERE title IS NULL` to persist. Between the read and the UPDATE there is a `sanitizeUserInput`-free Claude network round trip with no advisory lock, no `SELECT ... FOR UPDATE`, and no "naming in progress" sentinel column. Two requests arriving close together on the same never-named conversation (e.g., two open tabs, or a client retry that doesn't share the in-memory `namedRef` — different tab, different page load, or a mobile web view that reloads the component) can both pass the read-check and both burn a Claude call; only one UPDATE wins, so storage never diverges, but the org still pays for N Claude calls instead of 1 for that one naming event. This does **not** amount to "runaway" spend (each conversation can only race once — after the first successful UPDATE, every subsequent request 200s with no Claude call, per the passing idempotency tests), and `expensiveLimiter()` caps the practical blast radius per user. Recommend, when convenient: either a short-lived in-memory/Redis lock keyed on `conversationId` scoped to this route, or flipping the guard to a conditional `UPDATE ... SET title = 'PENDING_SENTINEL' WHERE title IS NULL RETURNING id` claim-first pattern before calling Claude. Not a blocker for this phase given the bounded blast radius and the existing rate limiter, but worth a follow-up ticket.
- **S-2 — no automated test pins the F-037 prompt's actual wording.** `conversation-prompt.test.ts` only tests the `cache_control` TTL-ordering invariant (an unrelated regression guard) and does not assert that `SYSTEM_PROMPT_HEADER`/`MODE_INSTRUCTIONS.casual` contain the brevity language. A future edit could silently regress the DEFAULT BREVITY / EXPAND ONLY ON REQUEST blocks (e.g., during an unrelated refactor) with no test catching it. A cheap substring assertion (e.g. `expect(buildConversationRequest(...).system[0].text).toContain('DEFAULT BREVITY')`) would close this without needing a live-model eval.

### NIT

- **N-1 — `docAttach.ts`'s injection-rejection path re-derives a `ValidationError` with fixed copy** (`'document contains content that cannot be sent to the tutor'`), which is correct and consistent with the "don't echo the marker" rule, but it's worth confirming (out of this review's file scope) that the client's file-upload error surface renders this specific 400 distinguishably from the generic "bad file" 400 so users aren't left guessing why a legitimate-looking `.txt` was rejected. Not checked here since it's client UI copy, not server behavior.
- **N-2 — `MODE_INSTRUCTIONS.casual`'s "Follow the default brevity rule (short turn, one follow-up question)" restates a subset of the header's own wording** rather than just referencing it (e.g., "see DEFAULT BREVITY above"), which is a minor duplication risk if the header's exact shape (1-3 sentences vs. "short turn") is later tuned independently per-mode. Low risk given both currently agree; flagging only because prompt-string duplication is the kind of thing that quietly drifts.

## Answers to the specific verification asks

- **Will F-037 actually produce concise replies without breaking tutor behavior?** Yes on both counts. The instruction is concrete (sentence-count anchor, explicit anti-padding rule, doubled reinforcement via the numbered rule list) rather than a vague "be concise," which is the shape of instruction that reliably works on instruction-following Claude models. Domain behavior — corrections, register enforcement, vocab tracking, the `<user_input>` anti-injection framing — is untouched or tightened (Rule 5 extends brevity discipline to `englishNote` without removing any existing rule).
- **Is the name-route idempotent / paid-call-safe?** Idempotent in storage and in the common case: verified by tests that a second call after a successful auto-name, or after a user rename, returns the existing title with `generated:false` and zero Claude calls. Not fully race-proof under true concurrent first-calls (S-1), but the exposure is bounded (one-time-per-conversation race window, capped further by the existing per-user rate limiter) — not a runaway-spend risk, and not a blocker.
