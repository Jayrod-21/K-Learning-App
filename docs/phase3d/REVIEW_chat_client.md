## Findings by Severity

### BLOCKER

- **B-1 — "+" attach menu is missing arrow-key/roving navigation and any close-on-Tab-out handling, so it can be left open and orphaned (`Chat.tsx:950–972`, render at `1944–1990`).** The menu's `useEffect` (armed only while `attachMenuOpen`) wires exactly two keyboard/pointer behaviors: `Escape` (closes + refocuses trigger) and outside `mousedown` (closes, no refocus). There is no `ArrowDown`/`ArrowUp`/`Home`/`End` handling to move focus between the three `role="menuitem"` buttons (which fall back to natural DOM tab order, since none carry `tabIndex={-1}` for a roving-tabindex scheme), and no `Tab`/`focusout`/`onBlur` handling at all. Concretely: open the menu (focus lands on "Camera" per `attachFirstItemRef`), press `Tab` twice to reach "Upload document," then `Tab` once more — focus moves to the composer `<textarea>` (the next element in DOM order) while the `role="menu"` popup **remains rendered and visually open**, floating above the composer with no visible connection to where focus actually is. This is a genuine WAI-ARIA menu-button conformance gap (the file's own header comment at lines 144–150 claims "It follows the WAI-ARIA menu-button pattern," which arrow-key navigation and a defined focus-exit behavior are both part of) and a real, reproducible UI defect (an orphaned floating control with no test covering the case). No test in `Chat.test.tsx`'s "Chat attach menu (F-035)" `describe` block (`1632–1682`) exercises `ArrowDown`/`ArrowUp` or a `Tab`-out — the gap is invisible to the suite as written. **Fix:** add roving-tabindex or `ArrowDown`/`ArrowUp` (with wraparound) to move focus among the three items, and either (a) close the menu on `Tab`/`focusout` when focus would leave the menu+trigger pair, or (b) trap Tab within the menu the way a native `<select>`/OS menu would, consistent with the APG menu-button pattern. Either resolves the orphaned-popup defect; (a) is the smaller diff given the "non-modal, no focus trap" design intent documented elsewhere in the header.

### SHOULD-FIX

- **S-1 — the file-upload generic-400 copy can't distinguish "wrong file type" from "content flagged by injection scan" (`Chat.tsx:337–355`, `docUploadErrorMessage`).** Every `400` from `POST /conversation/:id/file` — whether the cause is a non-UTF-8 byte, an empty document, or `sanitizeUserInput` rejecting the text as an injection attempt (confirmed as a real 400 path by the companion server review's finding N-1, `docAttach.ts`) — renders the same fixed string: *"That file couldn't be attached. Use a plain text (.txt or .md) file under 256 KB."* For a user who picks a genuinely well-formed `.txt` that happens to get injection-flagged, this message actively misleads them into re-trying the same (rejected-for-a-different-reason) file, or reformatting when reformatting won't help. This matches the project's established "never echo server prose" constraint and is the same bucketing `imageUploadErrorMessage` already uses, so it's a defensible, consistent choice — but it's worth a distinct fixed string (e.g., using the server's `code` field, which is present on the `ApiError`, to special-case a content-rejection code with different copy) rather than folding every `400` into "wrong format." Low urgency; flagging for the same reason the server reviewer flagged it from their side (N-1) — closing the loop between the two reviews.
- **S-2 — F-036's documented "failed naming call releases the latch, retries on next turn" behavior is untested (`Chat.tsx:1152–1157`, tests at `2201–2296`).** The `triggerAutoName` rejection branch is implemented exactly as documented (the `namedRef` Set is rebuilt without the failed conversation's id), but no test in the "Chat auto-naming (F-036)" block rejects a `nameConversation` call and then asserts a second turn re-issues it. All three tests in that block only exercise the success path and the already-succeeded no-repeat path. Given this is exactly the kind of latch logic that's easy to accidentally invert (e.g., swapping the release condition), a test here is cheap and valuable — the existing `hoisted.ref.nameCalls[n]?.reject(...)` plumbing used elsewhere in the file already supports it.
- **S-3 — header doc/code mismatch on outside-click focus behavior (`Chat.tsx:144–150` vs. `937–940`, `959–965`).** The header comment states: *"`Escape` or a click outside closes it and returns focus to the '+' trigger."* The actual code only does this for `Escape` (`closeAttachMenu(true)`); the outside-`mousedown` handler calls `closeAttachMenu(false)` — i.e., outside click does **not** refocus the trigger, and the shipped behavior (leave focus wherever the click landed) is actually the more conventional choice for this interaction (forcing focus back to the trigger after an outside click that may itself have activated something else would be surprising). Recommend fixing the comment, not the code — the code's choice is defensible and matches common menu-button implementations; the comment overstates what happens. Untested either way (the outside-click test at `1654–1667` only asserts the menu closes, not where focus lands), so this drifted silently.
- **S-4 — no test constructs a `ConversationRow` with a non-null `title` to exercise the "server-reported list title" tier of the F-036 precedence chain in isolation.** The precedence chain (`confirmedTitles → row.title → titles → fallbackTitle`) is fully correct as read, and the `row.title` tier is trivially a `??` fallback, but every fixture in the test file (`LIST`, `Chat.test.tsx:446–459`) sets `title: null`, and the two auto-naming tests that do exercise a real title go through `confirmedTitles` (via `getConversation`'s detail envelope or a `nameConversation` resolve), never through a list row's own `title` field with nothing else populated. Low risk given the trivial implementation, but it's the one link in the documented four-tier chain with zero direct coverage.

### NIT

- **N-1 — `.km-chat__engToggle`'s `cursor: pointer` (`Chat.css:20–25`) implies the whole label+switch row is clickable, but only the `<Toggle>` button itself has a click handler.** The wrapping `<span>` is not a `<label htmlFor>` and carries no `onClick`, so clicking directly on the "English · 영어" text does nothing — a minor false affordance. Either wrap the switch in an actual `<label>` (clicking label text toggles native controls) or drop the pointer cursor from the wrapper.
- **N-2 — the file-chip icon (`Icon name="upload"`, `Chat.tsx:2081`) reuses the same icon as the attach menu's "Upload document" item and the send-adjacent iconography**, which is fine visually but slightly overloads "upload" as a glyph for "this is a document" in the rendered turn; not a functional issue, purely a design nit, noting only because a `file`/`document`-specific glyph would read more precisely in the bubble.

### PRAISE

- **P-1 — the 409/stale-version handling on both upload paths is genuinely well-tested, not just well-implemented.** Both `Chat.test.tsx:1943` (image) and `2130` (document) don't stop at "an error message renders" — they set `hoisted.ref.detailVersions[42]` to a new server-side value, reject the upload with a 409, assert the fixed copy (and that raw server prose like "version conflict" never leaks), assert the history effect actually refetches (`getCalls.length` goes to 2), and — in the image test — go one step further and prove a subsequent send/retry actually rides the *refetched* version rather than the stale one. This is exactly the "tests exercise real behavior, not tautologies" bar the review brief asks for.
- **P-2 — the F-034 removal is thorough and evidence-based, not just "looks clean."** Every symbol named in the ticket (`DICT_*`, `WordPopover`, `defineEntry`, `mineWord`, `tapChain`, `HINT_STARTERS`) was grepped across the whole `client/src` tree, not just the changed file, and the CSS side was cross-checked line-by-line against the deleted `index.css` block — there is no dead code or orphaned styling left behind from the old in-chat dictionary feature.
- **P-3 — the abort/mount discipline is comprehensive and consistently applied.** History load, stream send, and both upload kinds each get their own `AbortController`, each aborted on unmount and on conversation switch, and every async continuation is guarded (`ctrl.signal.aborted` / `mountedRef.current`) before touching state — including the less-obvious lazy-start race (`lazyStartRef`) where two rapid sends on a brand-new thread correctly share one `startConversation` call instead of splitting into two conversations. This is exercised by real tests (`Chat.test.tsx:1134–1202`), not just asserted in comments.
- **P-4 — the sidebar title precedence chain is implemented exactly as documented, in one place, with a rationale for keeping `confirmedTitles` separate from the derived `titles` map** ("a separate map … keeps 'confirmed name' and 'derived guess' from ever being confused with each other," `Chat.tsx:610–613`) — this is a clean, low-risk design for a feature (auto-naming) that's easy to get subtly wrong via map-key collisions.
