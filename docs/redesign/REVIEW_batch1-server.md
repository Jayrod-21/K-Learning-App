## Summary verdict

**PASS WITH CONDITIONS**

## Findings

### BLOCKER
None.

### SHOULD-FIX

1. **No UNIQUE constraint backs the seed idempotency claim — track it as an explicit follow-up, not just a comment.** `vocabLists.ts:836-846` (docstring) and `:877-884` (NOT EXISTS gate). Two truly concurrent seed paths for the same `(user_id, vocab_entry_id, face='recognition')` — e.g. this route racing `POST /vocab/cards/init` or `POST /vocab/entries/:id/bank` for an entry that's also list-a member — can both pass the NOT-EXISTS check and insert two `vocab_cards` rows, since Postgres READ COMMITTED does not make a bare `NOT EXISTS` check + insert atomic across two independent transactions, and there's no unique index to catch it (confirmed: `grep` across `db/migrations/` shows a partial UNIQUE for grammar-production cards, `020_grammar_production_card_uniq.up.sql`, and for hanja cards, `050_hanja_cards.up.sql`'s `uq_vocab_cards_user_hanja_face`, but none for `(user_id, vocab_entry_id, face)`). Impact if it fires: the word shows up twice in the review queue and its FSRS history splits across two cards — annoying, not destructive, no cross-user leakage. This is genuinely the same debt `cards/init` already carries in production today (`vocab.ts:452-455`), so it's not a defect this PR introduces — but the PR is a second call site widening the exposure, and the fix is cheap: a partial `CREATE UNIQUE INDEX ... ON vocab_cards (user_id, vocab_entry_id) WHERE face = 'recognition' AND deleted_at IS NULL`, mirroring 020/050 exactly, then swap the NOT-EXISTS gate for `ON CONFLICT DO NOTHING`. Recommend opening that as a tracked follow-up ticket rather than letting it live only as a "no UNIQUE constraint" comment.

2. **Missing test: soft-deleted list on the two new routes.** `vocabLists.test.ts:629-793`. Every other route in this file that has a "404 on other-user list" test also has a sibling "404 after the list is soft-deleted" test (see `vocabLists.test.ts:193` for `GET /vocab/lists/:id`). Both F-113 routes correctly include `deleted_at IS NULL` in their ownership check (`vocabLists.ts:766` and `:822`), so behavior is right — but neither `describe` block for `/cards/due` or `/cards/seed` exercises the soft-delete path, only the other-user path. Cheap to add, closes the coverage gap to match the file's own established test pattern.

### NIT

1. **No index supports `vocab_cards.vocab_entry_id` as a join/filter target.** `vocabLists.ts:806` (`JOIN vocab_cards c ON c.vocab_entry_id = le.entry_id`) and `:875` (`c.vocab_entry_id = le.entry_id` in the NOT EXISTS subquery). There is no index on `vocab_cards(vocab_entry_id)` anywhere in `db/migrations/` (only `grammar_entry_id` has one, `001_core_schema.up.sql:776`). In practice the planner can still drive this efficiently off `ix_vocab_cards_due_queue (user_id, due_at)` (partial, matches this route's `user_id`/`due_at`/`deleted_at`/`suspended_at` predicates) and hash-join against the list's (typically small) entry-id set, so this is unlikely to be a real hot-path problem at current data volumes. Flagging only because it's the same gap `cards/init`'s NOT EXISTS (`vocab.ts:467`) already has — not a regression, just never closed.

2. **`cheapLimiter()` on a bulk-insert POST.** `vocabLists.ts:854`. `POST /vocab/lists/:id/cards/seed` can insert one row per list member in a single request; every other write route in this file (`POST /entries`, `DELETE /entries/:entryId`, `PATCH`) also uses `cheapLimiter()`, so this is consistent with file convention rather than a one-off oversight. Worth a second look only if list sizes are large enough that repeated seed-spam becomes a real cost concern — not blocking.

### PRAISE

1. **The per-list `FOR UPDATE` lock actually closes the most likely race.** `vocabLists.ts:864-872`. Locking the `vocab_lists` row before running the NOT-EXISTS/INSERT CTE means two concurrent seed calls *for the same list* (the realistic "double-tap the Add-All-to-Review button" case the ticket is about) serialize on the list row: the second transaction's `SELECT ... FOR UPDATE` blocks until the first commits, so it re-reads a post-commit NOT-EXISTS view and correctly inserts 0. This is a stronger guarantee than the SHOULD-FIX #1 gap above (which only applies cross-route/cross-list) and stronger than `cards/init`'s equivalent, which has no lock at all.

2. **F-112 JOIN is correct and non-multiplying.** `vocabLists.ts:359-362`. `LEFT JOIN vocab_entries v ON v.id = e.entry_id` joins on `v.id`, the table's PK — one row per membership guaranteed, no fan-out. `example_korean`/`example_english` correctly come back NULL for grammar/hanja rows (where `e.entry_id` is NULL by the migration-049 XOR) and for a vocab entry with no example on file, exactly as the doc comment states. Verified against `seedVocabEntry`'s existing `exampleKorean`/`exampleEnglish` opts (`server/tests/helpers/seed.ts:74-117`) — this helper predates the diff, so the new test (`vocabLists.test.ts:201-221`) is exercising real INSERT/SELECT round-trip data, not a mock.

3. **The due-queue predicate is provably safe against the vocab_cards target-XOR constraint** rather than by convention alone. `vocabLists.ts:806-814` omits the canonical route's `c.hanja_character_id IS NULL` and grammar-graduation guards, but that omission is sound: `ck_vocab_cards_target_xor` (`001_core_schema.up.sql:715-720`, extended to 5 legs by `050_hanja_cards.up.sql:106-112`) guarantees exactly one of `vocab_entry_id`/`grammar_entry_id`/`source_sentence_id`/`topik_item_id`/`hanja_character_id` is non-NULL per row — so any card the `c.vocab_entry_id = le.entry_id` join can match already has every other target column NULL by a DB-level CHECK, not just by application convention. The `c.face = 'recognition'` filter is likewise a no-op-but-correct belt-and-suspenders: every vocab-card-creating code path in the repo (`vocab.ts:477`, `:583`, `:727`, and this PR's own `vocabLists.ts:886`) only ever mints `'recognition'` — the only `'production'` cards in the schema are grammar-targeted (`grammarDrill.ts:409`), which can never carry a `vocab_entry_id` by the same XOR. Confirmed by reading the actual constraint SQL rather than trusting the docstring.

4. **The "byte-identical wire shape" claim in the F-113 due-queue docstring was checked against the actual client code, not assumed.** `vocabLists.ts:751-756` claims the client's `normalizeDueCard` adapter (`client/src/services/vocab.ts:257-280`) "works unmodified" against a response missing the `grammar_*` columns entirely (vs. the canonical route, which always includes them as explicit `null`). Verified: `normalizeDueCard` destructures those keys off the response object — in JS, destructuring a key that's simply absent from the JSON produces `undefined`, identical to what destructuring an explicit `null` produces for the `!= null` guards immediately below it (`vocab.ts:271-278`). The claim holds; this is exactly the kind of comment that could quietly rot into a client bug and it was worth the five extra minutes to confirm it doesn't.
