## Summary verdict

**PASS**

Zero blockers. `claimDelivery` is genuinely atomic and exactly-once, proven by a real-Postgres 8-way concurrency test that hard-asserts exactly 1 winner / 7 losers and cross-checks the row count in the table (not a soft check). F-093's client-only fix correctly removes the one drift vector the Settings screen could originate (Reset → localStorage `settings.notif` → PUT) by echoing `lastSyncedPrefsRef.current.notif` (server-sourced) instead; the deferred server-side source-of-truth migration is a legitimate expand/contract call, not a dodge — the `notif` field in the `/settings/prefs` blob (018) is genuinely wire-echo-only today (no functional consumer reads it; the real notification config lives in `notification_schedules`/052, edited via separate `/notifications/schedules` routes), so deferring its retirement leaves no live inconsistency, only pre-existing (unaffected) dead data. F-192's two tests exercise the real `buildGeneratedItem` catch site and would fail against pre-B1 leaky code.

## Detailed findings

### F-092 — exactly-once claim, verified

- **Atomicity**: `claimDelivery` (`server/src/services/notificationDelivery.ts:56-66`) is a single parameterized `INSERT ... ON CONFLICT (schedule_id, window_start) DO NOTHING RETURNING id`. The unique index from migration 063 (`db/migrations/063_notification_deliveries_claim_key.up.sql:61-63`) is the sole arbiter — there is no read-then-write gap (no prior `SELECT`/probe in the function). Win/loss is determined purely by whether `rows[0]` exists (`notificationDelivery.ts:67-70`), never by a caller-supplied flag — matches the module's own claim in its header comment.
- **Parameterization**: both `claimDelivery` (`notificationDelivery.ts:61-65`) and `settleDelivery` (`notificationDelivery.ts:100-104`) use `$1`/`$2`/... placeholders exclusively; no string interpolation of caller input anywhere in the file.
- **Claim/settle race**: `settleDelivery`'s `UPDATE ... WHERE id = $4 AND status = 'pending'` (`notificationDelivery.ts:100-104`) means a settle can only affect a row that is still pending — a duplicate/replayed settle call is a no-op (`rowCount === 0` → `settled: false`), never a second write to an already-terminal row. Tested directly at `server/tests/services/notificationDelivery.test.ts:196-218`, including the "does not clobber the terminal status" check.
- **8-way test genuinely proves it, not a soft check**: `server/tests/services/notificationDelivery.test.ts:130-153` — hard-asserts `winners.toHaveLength(1)`, `losers.toHaveLength(CONCURRENCY - 1)`, plus a direct `count(*)` re-query on the exact key. Runs against a real testcontainer Postgres with migrations applied (`server/tests/helpers/pg.ts`), so the UNIQUE constraint is actually enforced during the race, not simulated.
- **No caller wired yet**: confirmed via repo-wide grep — `claimDelivery`/`settleDelivery` have zero call sites outside the new module and its test, consistent with the header's stated scope ("no scheduler, no worker loop... a later ticket"). This is a primitives-only PR; there's no half-built sender to audit.
- **Schema completeness**: every `notification_deliveries` column without a DB-level default (`schedule_id`, `window_start`) is supplied by `claimDelivery`; `sent_at`/`provider_ref` (nullable) and `created_at` (defaulted) are correctly left to the DB. The `ck_notification_deliveries_sent_has_sent_at` CHECK (052) is respected — `settleDelivery` only supplies `sentAt` on the `'sent'` branch (`notificationDelivery.ts:96-98`).

### F-093 — partial deferral assessed as legitimate

- **What shipped is consistent, not a half-migration**: the server's `/settings/prefs` GET and PUT (`server/src/routes/settings.ts`) both still source/persist `notif` from the same JSONB blob (018) — nothing in this diff touches the server contract, so there's no read/write mismatch introduced. The only change is client-side: which local value is echoed back on PUT.
- **The drift vector is real and is now closed**: before the fix, the debounced-PUT effect keyed off `settings.notif` (the `SettingsProvider`'s localStorage-backed state, confirmed at `client/src/hooks/SettingsProvider.tsx:119-131` — `resetSettings` sets the whole `settings` object, including `notif`, back to `DEFAULT_SETTINGS` and persists it). Since F-040 removed all notification-toggle UI from this screen (per the file's own header, `client/src/pages/Settings.tsx:16-23`), the *only* way `settings.notif` could change was the Reset button — an Appearance action — silently smuggling a reverted `notif` into a debounced PUT triggered by an unrelated Appearance change (e.g. accent pick). The fix (`Settings.tsx:878-910`) sources `notif` from `lastSyncedPrefsRef.current.notif` instead, which is populated only from the server GET (`Settings.tsx:817-822`) or a prior successful PUT's echo (`Settings.tsx:725`) — the client can no longer originate a value for this field. The pre-hydration guard (`Settings.tsx:877`, `if (!prefsHydratedRef.current) return;`) closes the one gap where `lastSyncedPrefsRef`'s ref-initializer default (`settings.notif` at mount, `Settings.tsx:699`) could otherwise leak into an early PUT — no PUT is possible before that ref is overwritten with server truth.
- **New test proves the exact scenario**: `client/src/pages/Settings.test.tsx:737-796` seeds a server-stored `notif` that diverges from `DEFAULT_PREFS.notif`, clicks Reset, confirms no PUT fires from Reset itself, then triggers a real (accent) change and asserts the resulting PUT body's `notif` still equals the server-stored value, not the reset default. This is a faithful reproduction, not a synthetic check.
- **Is the deferred half a live bug?** No functional consumer reads `notif` from the `/settings/prefs` blob today: grep across `server/src` shows the only route touching it is `settings.ts` itself (round-trip only), and the file's own SECURITY/design comments (`server/src/routes/settings.ts:1-28`) and the Settings.tsx header (`client/src/pages/Settings.tsx:16-23`) confirm it's wire-echo-only — the actual notification schedule/timing configuration lives entirely in `notification_schedules` (052), read/written via the separate `/notifications/schedules` routes (`server/src/routes/notifications.ts`). Since F-092's claim/settle primitives (and any future sender) would consume `notification_schedules`, not this blob, the blob's staleness relative to the real schedule table is inert data, not a live bug affecting current behavior. Deferring its full retirement is the correct expand/contract call: doing it now would be a coordinated schema-and-contract change (GET/PUT semantics, `DEFAULT_PREFS` meaning, client mock shapes), not an expand-only batch.
- **Spot-checked the "~15 assertions would break" claim**: counted `notif`-touching fixture/assertion pairs in `client/src/pages/Settings.test.tsx` outside the new F-093 test: lines 648/675 (F-040 test), 699/733 ("echo verbatim" test), 865, 936, 1057, 1149, 1182 — seven distinct pre-existing test blocks each with roughly one fixture setup + one assertion keyed to the current blob-sourced `notif` contract (`DEFAULT_PREFS.notif` equality or a specific stored-notif echo). That's plausibly ~14 individual expectations, in line with the builder's "~15" figure — not an inflated excuse. Each would need rework (mock shape, assertion target, or removal) under a `notification_schedules`-sourced contract, confirming this is a genuine coordinated redesign, not busywork avoidance.

### F-192 — regression tests pin the real fix site

- **Raw-error test** (`server/tests/routes/diagnostic.test.ts:653-671`): throws a plain `Error` with a distinctive message (`'ECONNRESET: raw socket detail...'`) from the stubbed `generateDiagnosticItem`, asserts the response is `502` and that `body.error.message` does NOT contain the raw text. This exercises `buildGeneratedItem`'s catch (`server/src/routes/diagnostic.ts:525-547`): a raw error has no `httpStatus`, so `mapClaudeError` returns it unchanged (`mapped === err`, `server/src/middleware/errors.ts:162,178`), routing into the `else` branch that logs server-side only and throws a fixed-string `UpstreamError` (`diagnostic.ts:535-546`) — defaults to 502 (`errors.ts:96-105`). Against pre-B1 code (which the comment states used to embed `err.message` directly), this test would fail on the `not.toContain` assertions. Real pin.
- **ClaudeProxyError passthrough test** (`server/tests/routes/diagnostic.test.ts:673-691`): throws `ClaudeRateLimitError` (httpStatus 429, `server/src/services/claude/errors.ts:44-47`), asserts `429` + `error.code === 'upstream_error'`. Matches `mapClaudeError`'s 4xx-passthrough branch (`errors.ts:172-176`) exactly. Against pre-B1 flatten-always-to-502 behavior this would fail on the status assertion. Real pin.
- Both tests drive the actual route stack (register → `/diagnostic` → `/answer` → `/next` to force ordinal-3 generation) via the shared `walkToGeneratedOrdinal` helper, not a direct unit call — confirmed by tracing `buildGeneratedItem`'s only call site at `diagnostic.ts:624`, which is reached from the `/next` handler. No production code changes accompany these tests, consistent with the stated F-192 scope (test-only).
