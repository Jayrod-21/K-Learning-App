## Findings — BLOCKER / SHOULD-FIX / NIT / PRAISE

**BLOCKER:** none found.

**SHOULD-FIX:**
1. **F-142 trend-math has no numeric test.** All 3 new trend-line tests assert presence/count (`toHaveLength(1)`, `toHaveLength(0)`) gated on `n>=3` vs `n<3`, but none asserts the actual `x1/y1/x2/y2` (or the derived slope/intercept) the regression produces. If the slope formula were silently wrong (flipped sign, wrong denominator, off-by-one on `first`/`last`), every existing test would still pass. Recommend one test that reads the rendered `<line class="km-progress__trendfit">`'s `y1`/`y2` attributes (or a small extracted-and-exported `regressionTrend` unit test) against a hand-computed expected value for the `HISTORY_3` fixture (I hand-verified it: overall scores 42/53/67 → slope 12.5, intercept 41.5, so the line runs from y=41.5 at x=0 to y=66.5 at x=2 in score-space). *(Progress.test.tsx:312-325)*
2. **Trend line and the pre-existing TOPIK reference line are visually near-identical in light theme.** Both `.km-progress__trendfit` and the pre-existing `.km-progress__refline` resolve to `var(--paper-faint)` in light theme (only the dark-theme override differentiates them, `--paper-mute` vs `--paper-faint`). They're distinguished only by dash spacing (6 4 vs 4 3) — legible on close inspection but a soft failure mode if both lines are visible on the same chart. Consider giving the trend line its own token/opacity step in light theme too. *(Progress.css:112-117,154-161)*

**NIT:**
1. `SubwayProgress` for the attempt count (`current={n - 1}`, `steps={n}`) always renders 100%-filled with the last station in the `current` (ringed) state and never any `ahead`/hollow stations — a valid, defensible reading of "how many attempts banked so far," but it diverges from the prototype's TOPIK-compare subway (`km-prototype.html` line 215), which shows some hollow/ahead stations implying a target beyond the current count. Not a correctness bug — the component's own contract ("steps"/"current" is generic) is honored — just a design-fidelity judgment call worth a sentence in the PR description in case the design-fidelity reviewer expects the "goal ahead" reading.
2. `.km-progress__trendnote` and other caption text reuse `--paper-faint`, the same token already used for axis ticks/threshold labels elsewhere on this page (pre-existing pattern, not newly introduced) — flagging only because the design doc's WCAG-AA bar applies to "every" surface; this token's contrast wasn't re-audited as part of this diff and I didn't re-derive it, since it's an established convention already used on this exact page before this change.

**PRAISE:**
1. The refactor from `CompareCard`/`MasterySection`/`SkillTrendsCard` (`Card`-wrapping components) to `CompareCardBody`/`MasteryBody`/`SkillTrendsBody` (content-only, `Card` now supplied once by `CollapsibleTile`) is clean — no leftover double-`Card` nesting, no dead functions (`HistoryBlocks`, `SkillTrendsCard`, `MasterySection`, `CompareCard` all confirmed gone via grep, no orphaned references), no unused `Card` import.
2. `isNewBest()` (Progress.tsx:847-861) correctly requires `n>=2`, uses the *derived* Overall (not the last dimension found), and is properly exercised by 3 tests covering true/false/single-attempt cases including a specifically-crafted "prior best beats latest" fixture.
3. The doc comment explaining why `CityCard` was NOT adopted (`CollapsibleTile` hardcodes plain `Card` internally, and that's a shared component out of this page's scope) is exactly the right kind of self-aware trade-off documentation — it flags the deviation from the design doc rather than silently under-delivering.
4. `regressionTrend`'s guard commentary is honest about what's actually reachable (`den === 0` documented as unreachable-but-guarded given unique integer indices) rather than dead defensive code with no explanation.
5. `n<3` guard reasoning is stated as "a 2-point regression is identical to the raw line" — correct, and shows genuine understanding of *why* the fallback threshold is 3, not just a magic number.

## F-142 trend-math verdict (explicit)

**Correct.** Hand-verified against the `HISTORY_3` fixture (Overall/mean scores 42, 53, 67 at indices 0,1,2): mean x̄=1, ȳ=54; Σ(dx·dy) = (-1)(-12)+(0)(-1)+(1)(13) = 25; Σ(dx²) = 2; slope = 12.5; intercept = 54 − 12.5(1) = 41.5. Endpoints: x=0 → y=41.5, x=2 → y=66.5, both within [0,100] so clamping is a no-op here (clamp logic itself is correct and separately reachable for extrapolated/out-of-range synthetic data). The `n<3`/`den===0` guards are correct and cheaply verified. **However**, no test in the suite actually checks these coordinates — the 3 new F-142 tests only gate on element *count* (`0` vs `1` `.km-progress__trendfit` lines, `5` `.km-progress__dot--latest` markers), so a broken slope calculation that still produces *some* line would slip through the test suite undetected. This is the SHOULD-FIX above, not a BLOCKER, because I independently verified the shipped formula by hand and it is correct — but the test suite as written cannot catch a regression to it.
