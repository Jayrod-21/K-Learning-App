# Review: F-189 colors

Reviewer: independent senior reviewer (colors slice only). Scope: `LearnMenu.tsx/.css/.test.tsx`, `DancheongRail.tsx`, `styles/seoul-devices.css`, `styles/tokensContrast.test.ts`, plus the `tone`/color props on `pages/Today.tsx`. Branch `feat/phone-round4` @ `15fcbf3`, base `rebuild`. All hex values below were pulled from `client/src/styles/index.css` and cross-checked with a scripted WCAG-luminance + CIE76 ΔE calculator (not eyeballed).

## Summary verdict

**REQUEST CHANGES**

The AA-contrast claim is real and independently verified — every new cyan/violet pairing clears 4.5:1 in both themes, and the token-parsing tests (`tokensContrast.test.ts`) are genuinely rigorous, not tautological. Same-hue-both-surfaces holds for 4 of 6 canonical skills (Vocab, Hanja, Reading, Listening are byte-identical tokens in LearnMenu and Today) and is very close for the other 2. But two things fall short of "genuinely perceptually distinct" and one inline code comment makes a factual claim about the honeycomb geometry that is demonstrably false — all three are things the ticket's own stated goal ("fix the too-similar complaint") should have caught.

## Findings

### BLOCKER

1. **Reading (cyan) vs Listening (moss) are a near-collision in Day theme, and they sit directly side-by-side in Today's Carousel 2.** ΔE76 ≈ 21.5 (Day) — the smallest hue-to-hue gap of any pair in the whole 6-hue system, well under the ~25–30 ΔE floor conventional categorical palettes use for adjacent swatches. `--moss: #2E7D6B` / `--cyan: #256E7D` (index.css:113–116) are within 25 RGB units of each other at every tier — raw hue, `-ink`, and `-soft` alike (verified: raw ΔRGB=25.1, ink ΔRGB=28.7, soft ΔRGB=28.3). In Today's "Suggested learning" peek slider the DOM order is Listening → Reading → Writing (`Today.tsx` ~640–706), i.e. the two closest colors in the entire palette are adjacent tiles a user scrolls past directly, in the default (Day) theme. This is exactly the "lots of blue/green too similar" complaint the redesign was commissioned to fix, reproduced on a different pair. (Night theme is fine for this pair: ΔE76 ≈ 46.2.)

2. **Grammar (vermilion) and TOPIK (accent) are not merely "sharing a family" — the code's claim that they land non-adjacent in the honeycomb is false, and they render as literally the same CSS class.** Both key to `.km-learnmenu__hexwrap--vermilion` (`LearnMenu.tsx:169-177`, `HEX_HUE.topik = 'vermilion'`, `HEX_HUE.grammar = 'vermilion'`), i.e. identical `--hx-hue`/`--hx-ink`/`--hx-bg` — not "similar," *identical*. The comment (`LearnMenu.tsx:39-48`, repeated at `:110-138` and `:126-137`) asserts this is safe because "TOPIK row-2-center, Grammar row-1-right... land non-adjacent." Geometry says otherwise: `.km-learnmenu__comb` centers each row via `align-items: center` and rows nest with `margin-top: calc(--km-hex-w * -0.196)` (index.css:1261-1277) specifically so adjacent rows interlock. Working the actual layout math (hex width W, row2 = 3 tiles spanning `3W+24`, row1 = 2 tiles spanning `2W+12`, centered under row2): row1's right tile (Grammar) occupies `[1.5W+18, 2.5W+18]`, which straddles the valley between row2's center tile (TOPIK, `[W+12, 2W+12]`) and right tile (`ttmik`, `[2W+24, 3W+24]`). Grammar's hexagon literally touches TOPIK's. Two touching honeycomb cells rendered in the exact same color read as one fused vermilion shape, not two distinct skill tiles — undermining the entire "one skill, one color" premise this PR ships. This is not a new bug this batch introduced (the same false claim, and the same geometric adjacency, existed for Writing+TOPIK before this diff — see Coordination Observations below) but this batch is the one that had the explicit job of getting per-skill color right, touched this exact reasoning in 3 places, and re-asserted the same unverified/false claim rather than checking it. Minimum fix: correct the comments to stop claiming non-adjacency (a false claim actively misleads the next engineer), and ideally reorder `COMB_ROWS` so TOPIK isn't row-2-center (a position that, in a 2-3-2 layout, is geometrically adjacent to *all four* of its row-1/row-3 neighbors, not just Grammar).

### SHOULD-FIX

3. **Grammar/TOPIK resolve to near-but-different tokens between LearnMenu and Today in Night theme (not the "same" token the PR claims).** LearnMenu's `vermilion` hue reads `--vermilion-bright` (`index.css:1341-1344`); Today's `accent` tone reads `--vermilion` via `.km-tone--accent` (`seoul-devices.css:161`). In Day these are identical (`--vermilion-bright: var(--dan-verm)` == `--vermilion: var(--dan-verm)`). In Night they diverge: `--vermilion-bright: var(--neon-coral-bright)` = `#FF6B8A` vs `--vermilion: var(--neon-coral)` = `#FF3E6C` (index.css:235-238). Small, same-family difference, but it's exactly the "two near-but-different tokens" failure mode this review was asked to check for, and it affects both skills parked on the vermilion/accent family (Grammar and TOPIK). The other four canonical skills (Vocab/blue↔indigo, Hanja/ochre↔ochre, Reading/cyan↔cyan, Listening/mint↔moss) are byte-identical in both themes — confirmed by reading the token chains directly.

4. **Vocab (indigo) vs Writing (violet) is the tightest pair in Night theme and the second-tightest in Day** — ΔE76 ≈ 19.5 (Night), ≈ 22.6 (Day) — actually the single closest pair *system-wide* when both themes are considered together (cyan/moss recovers to 46.2 in Night; indigo/violet never recovers). `--indigo: #2B5F9E`/`--violet: #6B4E8C` (Day), `#5C87FF`/`#9B7CFF` (Night) — both blue-leaning purples, ~19–23° apart in hue. Lower real-world risk than Finding 1 because Vocab and Writing never appear in the same carousel or honeycomb row simultaneously, but it's still below the threshold the other 4 pairs clear by 2-4x, and is worth a note for whoever revisits this palette next.

5. **`--vermilion-bright` == `--vermilion` in Day theme makes "TOPIK stays accent" only fully correct under the DEFAULT accent preset.** If the user picks the `blue` or `mint` accent preset (`[data-accent="blue"/"mint"]` blocks, index.css ~393-428), `--vermilion`/`--vermilion-bright` re-point to `dan-cobalt`/`dan-jade` — i.e. TOPIK and Grammar (both "vermilion") become pixel-identical to Vocab (`indigo`, fixed to `dan-cobalt`) under the blue preset, or to Listening (`moss`, fixed to `dan-jade`) under the mint preset. This is a 3-way exact-hex collision, not just 2. It's not new — the same collision existed pre-diff with Writing standing in Grammar's slot — but F-189's own docs never mention the accent-picker interaction at all, so the "6 genuinely distinct hues" claim silently assumes the default preset. Worth a doc note at minimum; ideally the accent-tracking slot shouldn't reuse a hue any *fixed* skill token can independently land on.

6. **No single source of truth ties LearnMenu's `HEX_HUE` map to Today's scattered `tone=` literals.** They currently agree (verified by hand for all 7 sub-pages), but nothing enforces that beyond comments promising they match, in two files, with two different naming vocabularies for the same colors (LearnMenu: `indigo`/`moss`/`vermilion`; Today/CityCard/DancheongRail: `blue`/`mint`/`accent`). That naming split is exactly the kind of indirection that let Finding 3 (the Night-mode vermilion/vermilion-bright drift) go unnoticed. A shared `SKILL_HUE`/`SKILL_TONE` constant consumed by both call sites would make "same skill, same color, both surfaces" structurally guaranteed instead of comment-enforced.

### NIT

7. `LearnMenu.test.tsx`'s new F-189 test (`:50-91`) is well-built (real render, real DOM class assertions, real regression pin for the Writing/TOPIK collision) but its own docstring overclaims: "the SAME six skill→hue tokens Today's tile carousels consume." The test never renders or touches `Today.tsx` — it only asserts LearnMenu's internal map. Not wrong, just a claim the test doesn't itself back up; a companion assertion in `Today.test.tsx` (or the shared-constant fix in Finding 6, which would make the claim true by construction) would close the gap.

### PRAISE

- `tokensContrast.test.ts`'s `km-tone fill contrast` block (the new cyan/violet `DAY_COMBOS`/`NIGHT_COMBOS` entries) is real verification, not a rubber stamp: it parses the literal token blocks out of `index.css` at test time via regex, resolves `var()` chains, and computes actual WCAG relative-luminance contrast — a hex-value regression in a future re-tint would fail this test. Independently re-derived the same numbers by script: Day cyan 5.82:1, Day violet 6.79:1, Night cyan 11.18:1, Night violet 6.26:1 — all inside the builder's claimed 5.8–11.2:1 range, all comfortably above 4.5:1 AA.
- The `--ochre` "locked" treatment (fixed regardless of accent, same token both surfaces, `--km-mastery-*` left untouched) is correctly executed and correctly documented as orthogonal to the mastery triad (index.css ~106-150, unchanged by this diff — confirmed the entire `index.css` diff on this branch is the unrelated px→rem migration only, nothing color-related).
- `DancheongRailTone`'s expansion to include `cyan`/`violet` is a clean, low-risk change: the component just template-interpolates `km-tone--${tone}` (`DancheongRail.tsx:52-60`), so there's no switch/exhaustiveness trap that could silently no-op for the two new values.

## Coordination observations

- The Writing/TOPIK adjacency-and-collision problem this PR set out to fix and the Grammar/TOPIK adjacency-and-collision problem this PR leaves in its place are the *same underlying geometric fact* (row-2-center in a 2-3-2 comb touches all four of its row-1/row-3 neighbors) wearing different skill labels. Whoever owns the honeycomb layout next should treat "which skill sits in TOPIK's shared-family slot" as unfixable by relabeling alone — the fix is either a 7th dedicated hue for TOPIK or a layout change that moves TOPIK off row-2-center.
- This review's numeric pass surfaced two pairs (`cyan`/`moss` Day, `indigo`/`violet` both themes) that neither the ticket description nor this review's own initial brief called out by name — the brief specifically asked about `indigo` vs `cyan` (ΔE76 32.9 Day, 70.5 Night — actually fine) and `vermilion` vs `accent`/TOPIK (the identical-token issue, confirmed). Worth flagging to whoever assigned this batch that the two closest pairs weren't the ones flagged in the ticket.
- Finding 6 (no shared constant between `LearnMenu.HEX_HUE` and `Today.tsx`'s inline `tone=` literals) is the root cause that let Finding 3 ship undetected — recommend fixing that structurally rather than patching the Night-mode token choice in isolation, since the same drift risk exists for any future skill/hue reassignment.
