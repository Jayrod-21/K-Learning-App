## F-165 verdict (explicit) — the Anki loop

**Correct.** Traced by hand against the stated bar (no lost/duplicated chars, real state writes, honest cap):

- **Queue construction** (`buildDrawQueue`, Hanja.tsx:344-356): starts with the requested character, then appends `practicing` before `new` characters from the SAME fetched pool, deduped via a `Set`, capped at `DRAW_SESSION_LIMIT = 20` (242). Already-`banked` characters are never *added* to the queue (only ever present as the requested head) — deliberate, documented, and correct for "closer to mastery first" prioritization.
- **Right** (`judgeRight`, 2482-2492): computes `promoteState(current.state)` (332-335: `new→practicing`, anything else→`banked`); calls the REAL `onSetState` — which is the root's `onSetState` (454-468), the exact same callback the detail sheet's bank button uses (3049-3051) — **only when the state actually changes** (already-banked correct answers skip the write, a documented no-op). The queue head is then removed (`slice(1)`) and `masteredCount` increments. No parallel/fake mastery signal exists anywhere in this path.
- **Wrong** (`judgeWrong`, 2494-2502): destructures `[head, ...rest]` and returns `[...rest, head]` — the character moves to the back, is never dropped, never duplicated, and **no write fires** (verified: `setHanjaStateMock` asserted not-called in the corresponding test, Hanja.test.tsx:1125).
- **No double-promotion on wrong→right**: since a wrong answer never mutates `Hanja.state`, a character that's wrong N times then right once still promotes exactly one band (based on the *original* state, not a re-derived one) — the overlay only ever updates on a successful write, and `current` re-derives from the live (overlay-aware) `chars` array each render, so this can't drift.
- **Session-restart guard**: the `seededForRef` ref (2457) keys re-seeding on the requested character's identity, not just non-null — so an optimistic-overlay update to `chars` mid-session (which changes the `chars` prop reference) does NOT reset the queue. This is a real, non-obvious correctness detail and it's handled right.
- **Cap honesty**: `DRAW_SESSION_LIMIT = 20` is a hard `break` in the build loop (350) — genuinely bounded, not a rendering-only cap. `totalInSession`/`masteredCount` are both real counts derived from that same array, so `SubwayProgress` (F-170) can never show more than 100%.

One nuance worth naming, not a blocker: `masteredCount` increments on EVERY right answer, including a right answer on an already-`banked` character (a no-op write). The UI copy says "N of M **mastered**" (2639, 2568) — for an already-mastered reconfirmation this is technically "re-confirmed," not "newly mastered." This is a labeling imprecision, not a correctness bug (the code comment at 2631-2632 is honest about this: "stations 'done' are characters already mastered/re-confirmed"), and it can only arise when the drill is entered from an already-banked character — low practical impact. **SHOULD-FIX (label), not blocker.**

## F-167 verdict (explicit) — mastery-color AA + semantics

**Two real problems, both isolated CSS fixes.**

**1. Semantic mismatch: `new` (never-studied) is colored `--danger` (red).**
Hanja.css:99-107:
```css
.screen.km-hanja .km-hanja__grid .km-hanjacell--banked     { border-top-color: var(--moss); }
.screen.km-hanja .km-hanja__grid .km-hanjacell--practicing { border-top-color: var(--ochre); }
.screen.km-hanja .km-hanja__grid .km-hanjacell--new        { border-top-color: var(--danger); }
```
The mock (`km-learn.html:190-198`) uses three colors — green/`master`, yellow/`learn`, red/`trouble` — where "trouble" means *frequently gotten wrong*, a distinct concept from "never started." The real `HanjaState` domain type has only three bands (`new`/`practicing`/`banked` — confirmed in `services/hanja.ts` and `types/domain`); there is no "trouble"/lapse-count signal anywhere in the data model to back the mock's red state. The builder's mapping substitutes `new` for the missing "trouble" concept and paints it red. That is a real design-fidelity problem: a character the user has simply never touched will render as if something is *wrong* with it. It's also a regression — the PRE-EXISTING shared default for `new` (styles/index.css:2147) was `var(--paper-faint)`, a neutral gray, which correctly conveyed "not started" with no alarm connotation. The override in this batch replaces a semantically-correct neutral with an semantically-incorrect danger red.
**Recommendation:** map `new` to a neutral (e.g. `--paper-faint`/`--line-strong`, matching the pre-existing default) rather than `--danger`; reserve red for an actual "struggling" signal if/when one is ever tracked, or drop the third color entirely and ship two real bands (moss/ochre) + neutral, which is an honest reflection of the three-value data model.

**2. WCAG AA non-text-contrast failure, Day theme, `--ochre` border vs. the card background.**
Computed per WCAG 2.1 relative-luminance formula (SC 1.4.11, non-text UI components, 3:1 minimum): Day `--dan-ochre` (`#C98A1E`, styles/index.css:81) against the Day card background `--ink-1`/`--paper` (`#FAF6EC`, index.css:48) is **≈2.73:1** — below the 3:1 floor. For comparison, the color it replaced (`--vermilion` = `--dan-verm` `#C0492E`, the shared pre-existing default for `practicing`, index.css:2146) is ≈4.60:1 against the same background — comfortably compliant. Moss (`#2E7D6B`, ≈4.57:1) and the new `danger`-as-`new` (≈4.60:1) both pass in Day; every color passes easily in Night (all ≥5:1, since Night's neon hues are bright against a near-black card). So the ONE failing pairing is exactly the one this ticket newly introduces (Day, `practicing`, `--ochre`), and it fails specifically because this override swapped a compliant fixed-hue border for a non-compliant one, in the name of fixing a real, separate bug (accent-tracking drift on `practicing` — see below).
The code comment at Hanja.css:96-98 states: *"Both `--moss-ink`/`--ochre-ink`/`--danger-ink` ... and the raw hues here are WCAG-AA-checked token pairs already in production on Today/Progress."* This claim does not hold for the raw `--ochre` hue used as a border against the Day paper background — that specific pairing does not appear to have been checked, or was checked against a different (darker) surface than this page actually uses. `--ochre-ink` (`--dan-ochre-ink` `#8B5F15`, index.css:81), the darker "ink" variant, computes to ≈5.20:1 against the same background and would have passed comfortably — that variant exists and is already used for the caption text elsewhere on the page (Hanja.css:401 `.km-hanja__study-sound` family uses the analogous `-ink` pattern for vermilion), but wasn't the one reached for here.
**Recommendation:** swap `border-top-color: var(--ochre)` for `var(--ochre-ink)` (or a new dedicated day-safe token) at Hanja.css:103, re-verify contrast, and correct the "already checked" claim in the comment either way.

**What IS real and correct about F-167:** the underlying bug it fixes is genuine — `HanjaCell`'s shared `practicing` class colors off `--vermilion` (accent-tracking: coral/blue/mint), so before this override a "practicing" tile's color would silently change with the user's accent choice, which is exactly the kind of bug the design doc's "fixed semantic colors" contract exists to prevent. The `.km-hanja__grid` scoping (99) correctly limits the blast radius to only this page's index, and the specificity argument in the file header (Hanja.css:8-12) is sound — `.screen.km-hanja .km-hanja__grid .km-hanjacell--X` (0,4,0) does deterministically beat the shared `.km-hanjacell--X` (0,1,0) regardless of stylesheet load order. Both the intent and the mechanism are right; two of the three chosen color VALUES are wrong.

1. **F-167: `new` (never-studied) hanja are colored `--danger` (red), misrepresenting a neutral "not started" state as a warning/trouble state, and diverging from the design mock's actual semantic (red = "trouble"/frequently-wrong, a concept this app doesn't track).** Hanja.css:105-107. 2. **F-167: Day-mode `--ochre` border (practicing state) fails WCAG 2.1 SC 1.4.11 non-text contrast (~2.73:1 vs. the 3:1 minimum) against the Day paper card background, regressing a compliant color (`--vermilion`, ~4.60:1) that the override replaced.** Hanja.css:96-98 (claim), 102-104 (code); index.css:48, 81, 2146 (token values). I'm categorizing both under F-167 as BLOCKER per the review brief's explicit criteria ("mastery color not from real data / AA failure on mastery colors ... test can't catch its own bug" — the AA failure is real and the semantic-color choice actively misleads users about their own progress, which is the core promise of this ticket).

### SHOULD-FIX

1. **`masteredCount` label imprecision on an already-banked reconfirmation.** Hanja.tsx:2482-2492, 2639. "N of M mastered" over-states a right answer on an already-banked character as a fresh mastery event. Low practical impact (only reachable when entering the drill on an already-banked character); consider "reviewed" or similar copy, or simply leave as documented behavior if the team is fine with the current framing.
2. **Untested no-op-write branch.** See Test quality gap #1 above.
3. **Encountered-band stat chips still use accent-tracking `tone="vermilion"` for "Practicing" (Hanja.tsx:714, pre-existing/unchanged by this diff), while the index grid two paragraphs below now uses the FIXED `--ochre` for the identical state (F-167).** Under `data-accent="mint"`, `--vermilion-ink` resolves to the same `--dan-jade-ink`/mint-ink value as `--moss-ink` (index.css:113-114, 126-127, ~381-384) — so the "Banked" and "Practicing" stat-chip counts become the SAME green, while two rows down the SAME two states are correctly distinguishable (green vs. yellow) in the index grid. This is a pre-existing bug (not introduced by this batch — confirmed via `git show rebuild:...` the `tone="vermilion"` call is unchanged), out of this ticket's stated scope (F-167 only asked for index tiles), but worth flagging now since this batch demonstrably knows how to fix this exact class of bug three lines away and didn't propagate the fix to the sibling surface on the same page. Recommend a fast follow-up (or fold into whichever fix-pass addresses the F-167 BLOCKERs, since it's the same root cause and same file).
4. **F-164 doc-comment overclaim.** Hanja.css:45-47 says the two clamped glyph squares are "the only two literal-px risks on the page" — `.km-hanja__study-square` (132px fixed, CSS:376-385) is a third. Not a real overflow risk at any supported viewport width (132px is well under a 320px minimum), so no functional fix needed — just tighten the comment's claim.

### NIT

1. **Doc-comment imprecision on the tone-enum workaround.** Hanja.tsx:42-45 states every CityCard/CollapsibleTile-city surface falls back to `plain` without noting the two `SubwayProgress` instances deliberately chose `accent` instead — a reasonable, different decision, just not what the blanket sentence implies. See workaround (b) above.
2. **`SealStamp`'s `tone="accent"` on the two milestone stamps (deck-clear at 1392, drill-complete at 2558) is a nice touch that DOES track the user's real accent** — worth calling out only because it's the one character-device on this page that intentionally didn't take the `plain` fallback, and it's the right call (a milestone celebration reading in the user's own chosen color is more "reward," a mastery-state indicator reading in the user's arbitrary color choice is more "confusing" — the page is internally consistent about which is which, it's just not spelled out anywhere that this distinction was made on purpose).

### PRAISE

1. **The `seededForRef` re-seed guard (Hanja.tsx:2457-2474) is a genuinely subtle, correctly-handled race.** Without it, the optimistic-overlay write from a right answer (which changes the `chars` array reference) would re-trigger the queue-build effect and silently reset the entire draw session mid-drill. The fix (keying on the requested character's identity, not just "seeded at all") is exactly right, and the doc comment explains the WHY, not just the WHAT.
2. **The no-op-write skip on an already-banked correct answer (2486-2489) is a real, deliberate correctness decision, not an oversight** — it avoids a pointless network round-trip AND avoids the (unlikely but real) failure mode of a write erroring out on a character that didn't need to change. Documented at 328-330.
3. **`HanjaCell`'s "+"-button-as-sibling-not-nested-child** (Hanja.tsx:1007-1011) correctly avoids invalid nested-`<button>` HTML by positioning the quick-add control absolutely inside a wrapper `div`, rather than nesting it inside `HanjaCell`'s own button — the comment explains exactly why a button-in-a-button would be both invalid and untappable, which is the right level of rigor for a subtle a11y trap.
4. **F-168's duplicate-membership (409) handling reads as information, not failure, consistently across BOTH the quick-add sheet and the existing `AddToListTile`** (1090-1096, 3154-3159) — the same UX decision applied twice without drifting into two different copy/behavior patterns.
5. **The threat-model and data-flow doc comments at the top of both `services/hanja.ts` and `Hanja.tsx` are exceptionally thorough** — CSRF, IDOR, path-injection, and "what's real vs. optimistic" are all named explicitly rather than left implicit, which made this review substantially faster to verify against the actual code.

## Coordination observations
