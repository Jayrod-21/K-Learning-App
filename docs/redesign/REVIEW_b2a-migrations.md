# Review

Branch `feat/beta-phaseB2a-dbhardening` @ `fe73c0c`, base `rebuild`. Scope: `db/migrate.py` (F-088 explicit destructive marker), migrations 062 (F-089, TEMP revoke), 063 (F-092, `notification_deliveries` claim key), 064 (F-093, backfill from the 018 prefs blob), `db/migrations/README.md`, `db/tests/*`.

Reviewer stance: this Postgres is **live and shared** by both blue/green colors with real user data. The lens throughout is "what happens when this migration hits the populated prod DB," not "does it work on an empty testcontainer."

## Summary verdict

**PASS.**

Both live-data risk questions the ticket calls out resolve favorably:

- **063 on a populated `notification_deliveries`:** the migration does **not** default/backfill — it relies on the table being empty. I verified independently (not just trusting the comment) that no code path writes to `notification_deliveries` today: `server/src/services/notificationDelivery.ts` (new in this branch) defines `claimDelivery`/`settleDelivery` but nothing calls them (no route, no scheduler, no cron); a repo-wide grep for `INSERT INTO notification_deliveries` outside that file and its own tests returns nothing. I additionally proved empirically (see "Verification performed" below) that if the table *did* hold a row, the migration fails atomically and safely — `NotNullViolation`, exit code 2, `schema_migrations` row NOT written, `window_start` NOT added — no partial state, no data loss, no silent corruption. So this is safe under the assumption AND fails safe if the assumption is ever wrong.
- **064 backfill:** idempotent (`ON CONFLICT DO NOTHING`, keyed to the real `uq_notification_schedules_user_kind_channel` constraint), defensively guards a malformed/legacy blob via `jsonb_typeof` (does not abort the migration/deploy on garbage), and correctly leaves any pre-existing real schedule row untouched. I ran the real migration chain (001→064) against a throwaway Postgres 16 testcontainer, seeding real user rows with realistic/malformed blob shapes, and all scenarios in `db/tests/test_migration_064.py` pass.

0 BLOCKERs. 2 SHOULD-FIX (both about the `down` migrations' precision/coverage, not the forward/deploy path). 3 NITs. Several PRAISE items — this is unusually well-defended migration work.

## Findings

### BLOCKER
None.

### SHOULD-FIX

1. **064's down-migration can delete a genuine pre-064 user row that happens to match the backfill shape exactly** (`db/migrations/064_backfill_notification_schedules_from_prefs.down.sql:373-398`). The `created_at = updated_at` guard distinguishes "never edited since insert" from "edited," but it cannot distinguish "inserted by the backfill" from "inserted by a real, single `PUT /notifications/schedules` call that happened to land on the exact same kind/channel/blob-intent combination and was never touched again." The migration's own header candidly documents this as an accepted imprecision (mirroring 046.down's precedent) — I'm not flagging it as new information, just confirming the risk is real (the `/notifications/schedules` route already ships in prod today per Settings.tsx, so genuine pre-064 rows of this shape are plausible, not hypothetical) and recommending it be tracked rather than silently accepted. A stronger fix (out of scope for this PR): have 064's up-migration tag the rows it inserts (e.g., a transient marker column, or log the affected `(user_id, kind)` pairs to a side table) so the down can target exactly what it created. Not a blocker because: (a) down migrations require `--allow-destructive` and are a deliberate, rare operation, not part of the forward deploy path; (b) the imprecision is documented in-file, not hidden.

2. **No round-trip (`up → down → up`) test for 064**, unlike 062 and 063 which both have one (`test_062_up_and_down_apply_without_allow_destructive`, `test_063_re_up_is_clean_on_an_empty_table`). `db/tests/test_migration_064.py` tests up-scenarios thoroughly and one down-scenario (preserves an edited row), but never re-applies `up` after a `down` to confirm the backfill re-derives cleanly from the still-present blob. Given the up-logic is a stateless re-derivation from `users.preferences` (not dependent on any "already ran" flag beyond the unique-constraint `ON CONFLICT`), this is very likely fine — but it's an easy, cheap test to add and closes the gap between "I'm confident" and "it's proven," matching the bar the other two migrations in this same PR already meet.

### NIT

1. `db/migrations/064_backfill_notification_schedules_from_prefs.up.sql:447-451` — the "WHY ON CONFLICT DO NOTHING" comment's first sentence ("any user who has ALREADY interacted... even just once, on any kind/channel... keeps their own row untouched") reads as if ANY interaction disables backfill for the WHOLE user. The actual behavior (confirmed by the SQL and by `test_064_does_not_overwrite_an_existing_schedule_row`) is per-`(user, kind, channel)` granularity — only the specific kind with an existing row is skipped, siblings still backfill. The comment's second sentence clarifies this correctly, but the first sentence should be tightened to avoid a future reader mis-generalizing the guarantee.

2. `db/migrate.py:349-352` (`MIGRATE_DIRECTIVE_PATTERN`) anchors on `^\s*--\s*migrate:...$` with `re.MULTILINE`, requiring the directive be the *entire* line (leading whitespace only, nothing trailing but whitespace). That's a reasonable, tight grammar, but it means a directive placed at the end of a longer comment line (`-- some prose -- migrate: destructive`) silently falls through to `None` (undeclared) rather than erroring — a migration author who gets the placement wrong doesn't find out until someone notices the sniff took over. Since this is exactly the kind of mistake F-088 exists to make impossible, consider a lint/CI check (e.g. `sqlfluff` custom rule or a small script) that greps for `migrate:` appearing anywhere in a migration file and asserts it's on its own line matching the pattern, so a malformed directive is caught at review time instead of silently degrading to the legacy sniff.

3. `db/migrations/062_revoke_km_app_temp.up.sql` / `.down.sql` — the two `DO $$ ... END $$` blocks are independent statements (not sequenced by an explicit dependency), which is correct given both must succeed for the migration to commit atomically, but a reader skimming quickly could mistake this for a two-step process where step 2 depends on step 1 succeeding within the same block. A one-line comment noting "these are independent, order is documentation-only" (the file's prose already implies this but doesn't say it explicitly) would remove any ambiguity for a future editor.

### PRAISE

1. **F-088's authoritative-marker design is genuinely well-conceived and well-tested.** The explicit `-- migrate: destructive|non-destructive` directive correctly takes precedence over the legacy regex sniff, closes real gaps the sniff can't catch (mass `DELETE FROM`, `DROP COLUMN` — both real, cited, pre-existing examples in 046/041), and — critically for a *gate-changing* PR — the backward-compat claim ("001-061 classify UNCHANGED") is independently true: none of those files carry the new directive (only 062/063/064 do), so `explicit_destructiveness` returns `None` for all of them and `contains_destructive` falls through to the byte-identical legacy `DESTRUCTIVE_PATTERNS` check. I ran the full existing `db/tests/` suite (109 passed, 3 pre-existing/environmental failures unrelated to this PR — see "Verification performed") and nothing in the 001-061 migration set changed classification.

2. **The string-literal-forging guard is correct and tested both directions.** `_strip_string_literals_only` strips quoted/dollar-quoted literals but keeps comments (opposite of `strip_sql_noise`), so a `COMMENT ON ... IS '... -- migrate: non-destructive ...'` can't forge a false marker, while a real directive comment is still found. `test_marker_inside_string_literal_is_not_forged` (db/tests/test_migrations.py:1656) proves this directly.

3. **`ConflictingDestructiveMarkers` refuses to guess.** A file declaring both directives raises rather than picking a default — the only safe behavior for a self-contradictory declaration, and it's unit-tested (`test_conflicting_markers_raise`).

4. **The dry-run destructive gate change is a genuine defense-in-depth improvement, not just decoration.** `cmd_migrate`/`cmd_rollback`'s `--dry-run` path evaluates `contains_destructive` on the *planned* bodies (`db/migrate.py:576-602`, `634-655`), so a deploy's dry-run step aborts on a newly-added destructive migration (or, now, an explicitly-marked one like 063/064's downs) before the apply step ever runs — matching the documented ADR-010 amendment.

5. **063's empty-table assumption isn't just asserted, it's actively defended.** The up-migration's header explains *why* the table is empty (052 shipped it that way, no sender exists), the test suite proves the schema behaves correctly on that assumption (NOT NULL rejects a null insert, UNIQUE rejects a duplicate claim, re-up after down is clean), and — as I verified independently — the failure mode if the assumption were ever violated is a clean atomic abort, not silent corruption. This is exactly the posture a live-data migration should have.

6. **064's defensive `jsonb_typeof` guards are real, not decorative.** I confirmed via `test_064_malformed_intent_value_does_not_abort_and_is_treated_false` (and independently by running it against a real Postgres 16 testcontainer) that a hand-edited/legacy blob with a non-boolean value at an intent path does not abort the migration and does not backfill for that key — exactly the fail-safe direction the comment claims, proven, not just asserted.

7. **F-093's scope discipline is honest and correctly expand-only.** `BUGS_AND_FEATURES.md`'s F-093 entry is explicitly marked "partial," documents exactly what was deferred (the `/settings/prefs` GET/PUT contract still round-trips the blob's `notif` keys verbatim — the CONTRACT step), and explains why (it would break ~15 existing route-contract assertions and is a bigger coordinated change than an expand-only batch should carry). The blob is never dropped or altered in this PR — confirmed by inspecting all four new/changed SQL files; nothing here touches the 018 column definition. This is exactly the discipline the task's "expand-contract" requirement calls for.

8. **The client-side companion change (`Settings.tsx`) closes the one live drift vector at the same time the backfill runs.** The outgoing prefs PUT now echoes `lastSyncedPrefsRef.current.notif` (last server value) rather than `settings.notif` (the independently-revertible localStorage cache), so after this deploy the blob's `notif` slice can no longer diverge from what 064 backfilled against. Good sequencing: the one-time snapshot read and the client change that stops new writes ship together.
