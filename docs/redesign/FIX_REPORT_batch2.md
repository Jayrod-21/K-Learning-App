## F-152 disposition (asked for explicitly)

**Did `graduated_at` exist on the client?** Yes — `BankedGrammarRow.graduated_at: string | null` (`client/src/types/domain.ts`) is already returned by `GET /grammar/bank` (`grammarService.listBanked()`) and was already being fetched by `ReviewGrammar.tsx` on mount; the pre-fix-pass code fetched it and then **discarded** it, folding every bank row into one `mastered` set regardless of `graduated_at`. No client or server change was needed to get the real signal — only to stop throwing it away.

**Label decision landed (per the orchestrator's mid-task correction — verbatim terms used):**
- The add-to-bank ACTION reads **"Add"** (Korean: 추가), and its state after a successful add reads **"Added"** (추가됨). Pending state: "Adding…"/추가하는 중….
- **"Mastered"** (숙달 / 이미 숙달됨) + the milestone `SealStamp` render **ONLY** when the pattern's bank row has `graduated_at !== null` — i.e. actually graduated via the LEARN Grammar screen's real drill/graduate flow (F-063), never on a fresh add.
- Two internal state sets replace the old single `mastered` set: `added` (every bank row, regardless of graduation) and `graduated` (the subset with `graduated_at !== null`). `CityCard` tone, the row action's variant/label/`aria-label`/`aria-pressed`, and the detail Sheet's action all key off the correct one of the two.
- Server contract untouched: `bankPattern`/`listBanked` are called exactly as before; this was a pure client-side gating + copy fix.
- A 409 ("already in the bank") and a plain 200 both keep the optimistic flip in the `added` set only — neither is ever promoted to `graduated`, since neither response carries a `graduated_at`. Faking that would be exactly the dishonesty this fix removes.

## A bug found and fixed during this pass (not in any of the 4 reviews)

Moving `MyVocabLists`' create form into a `Sheet` initially reproduced a real, user-facing bug: typing into the "New list name" input inside the new Sheet dropped every character after the first. Root cause: the create form's own keystroke state (`newName` etc.) lived in the SAME component that constructed the `Sheet`'s `onClose` as an inline arrow function; every keystroke's `setState` re-rendered that component, producing a new `onClose` reference, which re-ran `useModalA11y`'s open/close effect (its dependency array includes `onClose`) on every keystroke — and that effect's cleanup unconditionally restores focus to whatever was active before the sheet opened, silently kicking focus back out of the input after the first character. Fixed by extracting the form into its own `CreateListSheet` sub-component (mirroring the codebase's existing `ListDetailSheet`/`AddToListSheet` split) so keystrokes only re-render the child, never the parent, and `onClose` stays referentially stable across the whole typing session. Verified via a minimal isolated repro before and after the fix. This is exactly the class of bug the task's "atomic, run the FULL suite after the riskiest changes" instruction was meant to catch — flagging it explicitly rather than letting it ride as an invisible diff.
